Append new entries at the bottom. A decision is written as: date, context, options considered, decision, and what it commits the project to in the long term. ### D21. Contract architecture (11 October 2026)
Context: the plan for the contracts was reviewed before construction and each point below was checked against the paper.
Decisions:
1. **One value gate.** Every path that moves value (L1 in `submit`, queued L2 execution, approved L3 execution, `runSchedule`, sweep, fee top-up) goes through one internal function that re-checks, at the moment value moves, freeze, mandate expiry, payee still active, current limits, current capsule restriction and affordability. A queued item becomes executable at `max(storedExecuteAt, queuedAt + current Δ)`, so lengthening Δ delays items already queued and shortening never brings them forward.
2. **Schedule terms are signed.** For SCHEDULE_CREATE the Intent's `purposeHash` must equal `keccak256(abi.encode(SCHEDULE_TERMS_TYPEHASH, period, firstDue, maxRuns))`, which the contract recomputes. Schedules are bounded in number, the period is bounded below, and each due occurrence runs at most once.
3. **Obligation reference is bound.** For PAYMENT the Intent's `scheduleId` field is a 1-based obligation reference (0 means none). It is accepted only if the obligation is unsettled, for the same payee and for exactly the same amount, and it is settled before the token transfer.
4. **Fee top-up has a budget.** The mandate holds a per-top-up cap, a daily native budget, the agent balance floor and a native reserve the wallet keeps. A top-up sends at most the agent's deficit below the floor within those bounds. All four fields take part in the tightening comparison.
5. **Vault keeps accounts per wallet.** `SavingsVault` records `balances[wallet]`. Withdrawal debits only that wallet's balance and only for that wallet's owner.
6. **Complete partial order on the mandate.** Every field has a stated tightening direction, including horizon H (longer is tighter), refill period (longer is tighter), the fee fields and the channel profile (a superset of channels is tighter, compared as sets). A mixed update with any looser field must go through Λ.
7. **Capsules fail closed.** The wallet syncs new capsules from the bulletin in bounded chunks into its own bounded list of unexpired capsules. While a backlog remains, or if its list is full, every request is raised to at least L2. Anyone may call the public sync to clear a backlog. Allowance halving happens during sync, once per newly seen applicable capsule.
8. **Separate enums.** Intent tasks and capsule actions are distinct Solidity enums with an explicit mapping. FEE_TOPUP has no capsule action and is never matched, because it can only send a capped amount to the agent's own address.
9. **Typed owner proposals.** Loosening uses typed functions (`proposeAddPayee`, `proposeMandate`, `proposeRemoveObligation`, `proposeAgent`, `proposeGuardian`, `proposeUnfreeze`) that write a common time-lock record. There is no generic `bytes` dispatcher.
10. **Bulletin trust.** The registrar is immutable, set at deployment. "A second wallet" means a distinct registered wallet address.
11. **Versioning.** Each contract has a `VERSION` constant and the EIP-712 domain carries it. All owner state is readable through view functions so the owner can migrate to a later version.
12. **A guardian signature is required for every submission**, not only L1. This is stricter than requiring it only where an unsigned intent must not execute. Without the signed band, source and flags the contract has nothing to decide L2 or L3 on.
13. **Contract size** is measured with `forge build --sizes`. If `PolicyWallet` exceeds the EIP-170 limit, the fix is simpler logic or a linked external library, not an internal library.
14. **Invariant split by asset.** MockUSD may leave only to an active payee or the fixed vault, native token only to the current agent within the fee budget, with an affordability ghost check.

### D23. Choices made while building the contracts (12 October 2026)
1. **Size.** The first complete `PolicyWallet` was 37,368 bytes, above the EIP-170 limit of 24,576. Options measured: optimizer runs 1 (saved about 0.5 KB), via-IR (34,765 bytes), linked external libraries. Decision: six linked external libraries operating on storage structs (`AuthorityLogic`, `LedgerLogic`, `CapsuleLogic`, `DecisionLogic`, `ItemLogic`, `IntentLogic`), the pattern Aave v3 uses. The wallet is 22,054 bytes. The value gate (`_decide` then `_move`) stays in `PolicyWallet.sol`. Events and errors live in `IPolicyWalletEvents` and `IPolicyWalletErrors`, so logs appear at the wallet address. Commits the project to: every deployment deploys and links the libraries. The Python runner and the evidence run must link them, and the library deployments are extra transactions in E01.
2. **No setup shortcut.** Only the first `setMandate` is immediate. Even the first payees wait Λ. With the demo profile, wallet setup waits 300 s.
3. **Owner key is fixed** for the life of a wallet. Migration means a new wallet. `revokeAgent()` is immediate (tightening), and a new agent arrives through `proposeAgent` and Λ.
4. **Schedules.** Minimum period 1 day, at most 16 schedules, `maxRuns` at least 1, `firstDue` not in the past. Each occurrence is a fresh obligation. A run is not charged to the allowance, because its terms were decided when the schedule was created. A run is matched against capsules as a PAYMENT with the flags the contract derives itself. A held occurrence stays due. `cancelSchedule` is immediate, but the open obligation stays until removed through Λ.
5. **What d1 counts.** L1 executions and schedule runs. L2 and L3 executions and sweeps do not count, because they were delayed or approved by the owner.
6. **Sweep and fee top-up tiers.** A sweep is L1 on q1 and q2, and a sweep above D reverts. A fee top-up sends the smallest of the requested amount, the cap, the agent's deficit below the floor, the rest of the daily budget and the balance above the native reserve, and reverts if that is zero.
7. **Deciding check** is the lowest-numbered check that demanded the final tier. Check 4 is reported only when the allowance step raised the tier.
8. **Pending items** are re-assessed when executed and revert with `NoLongerAuthorised` if the tier now is above the tier they were authorised at. An approved L3 item gets Π if a full capsule match appears after approval. `extendHold` works on L2 and L3 items.
9. **Allowance precision.** Kept in fixed point, 1e6 per point, so refill is smooth.
10. **Capsules.** Applicability is decided at sync time against the channel profile then in force. Up to 8 capsules are synced per call and at most 16 tracked. When the list is full the cursor stops and every request stays at L2 or above until capsules expire. Bulletin constants: lifetime at most 7 days, 3 publications per wallet per day, quorum 2. Model versions must strictly increase.
11. **Interfaces.** `submitSchedule(intent, terms, att, sig)` for T2, `submit` for the other tasks, `executePending(id)` for queued and approved items. The mission text is emitted in `MissionStated`, not stored. `mandateHash = keccak256(abi.encode(keccak256(bytes(mission)), mandate))`.
Known limits, carried into the security self-assessment: widening the channel profile does not apply capsules already passed over. Enough applicable capsules can hold every wallet at L2 (only ever more cautious, bounded by the registrar and the publish limit). A compromised agent can fill the obligation registry, which only lowers D.

### D24. Fixes after the contract review (12 October 2026)
Context: a review of the contracts found one serious issue and five lesser ones. Each fix has a test that fails when the fix is reverted.
1. **Stale proposals.** A mandate proposal records the mandate hash it was built on and goes stale if the mandate changes (`ProposalStale`). Unfreeze, add-payee and agent proposals record counters for freeze, payee removal and agent revocation, and go stale when the counter moves. Counters, not timestamps, because a freeze and a proposal can share a second. A freeze makes every pending loosening stale.
2. **Full capsule list.** The weakest tracked capsule (lowest current restriction, then fewest attestations, then soonest expiry) gives up its slot to a stronger newcomer. A capsule left without a slot keeps every request at L2 or above until it expires, and never higher, so a single observer still imposes at most a delay.
3. **Widening the channel profile** rewinds the sync cursor to the first capsule that may still be live (`ThreatBulletin.firstPossiblyLive`) and rescans. Each capsule is marked seen, so the allowance is never halved twice for one capsule.
4. **Approved L3 affordability.** `approve` records q2 at that moment and refuses while the item is blocked (for example frozen). Execution refuses if q2 is worse than at approval (`NoLongerAffordable`).
5. **Obligation slots.** The agent may hold at most 12 open obligations. With 16 schedule slots, the owner always keeps 4 of the 32.
6. **Decision event** on `executePending` and `runSchedule` too. A schedule run carries a zero intent hash, and the `ScheduleRan` or `ScheduleHeld` event that follows names the schedule.
7. **Bounds.** An attestation is valid for at most 15 minutes. Δ and Λ are at most 30 days, Π at most 7 days, so a tightening cannot lock the owner out. Owner, agent and guardian must be three distinct addresses, checked at deployment, at proposal and after a key change is applied.
8. **`test_NoArbitraryCall`** compares the compiled ABI with a reviewed list of 77 signatures and rejects any generic-call shape. `foundry.toml` grants read access to `./out` for this.
PolicyWallet is 23,494 bytes after these fixes, 1,082 under the limit.

### D25. Agent runtime architecture (12 October 2026)
Context: the runtime plan was challenged before construction and each point below was checked.
1. **Guardian is a separate process from the start.** Options: in-process object with an import-graph test (rejected, because an import graph is not a security boundary and the process would hold both the agent and guardian keys), or a separate process. Decision: `python -m agentvax.guardian.service` runs as a child process speaking line-delimited JSON over its standard input and output. It loads or generates its own key and is the only process that ever reads it. It reports only its address. One guardian instance is bound to one wallet address and chain id. It derives `source`, the detector band and the pressure flags itself from the raw content, and accepts other flags from its caller only as additions (adding a flag only tightens). `validUntil` is the latest block time plus the attestation lifetime.
2. **Pressure phrases run on raw content** inside the guardian and, as a deterministic rule, in the runtime. Raw content reaches no planner, no memory and no model other than the reader.
3. **Model calls are stateless and fail closed.** Each call carries only its own messages, no conversation state is kept, every reply is validated against its schema before use, and a provider error never falls back to `MockLLM`.
4. **One hosted provider.** An OpenAI-compatible chat endpoint with JSON-schema output, configured by `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY` and `LLM_BASE_URL`. It covers OpenAI and the many providers that offer this interface. The adapter protocol stays provider-neutral.
5. **MockLLM** lives in `agentvax.harness.mock_llm` with its rule tables as data. It is constructed only by the evaluation runner, the tests and a separate demonstration entry point (`python -m agentvax.api.demo`), which labels everything `mock`. `python -m agentvax.api.app` has no import path to it.
6. **Strict boundaries.** Every boundary model is strict, forbids extra fields and is immutable. Shared on-chain primitives live in `agentvax.types`. Models owned by one boundary (reader output, planner decision, capsule draft) live with their module. `IntentDraft` is distinct from the signed `Intent`, and `CapsuleDraft` from the on-chain `Capsule`. `ScheduleTerms` travels with a schedule draft and its `purposeHash` is computed deterministically before signing.
7. **Planner questions are codes.** The planner returns a `QuestionCode` with typed parameters, rendered from `strings.json`. No model text is shown to the user.
8. **Memory** is a closed schema of enums, bounded numbers, hashes, timestamps and on-chain identifiers, written only by deterministic code, stored in SQLite with a schema version. Any fact from memory that shapes an intent sets MEMORY_SOURCED.
9. **Detector model files** are canonical JSON of numbers. No pickle and no object arrays. The hash anchored on chain is the keccak of the exact canonical bytes, and dimensions and finite values are checked on load. The hashing encoder is the offline encoder used for tests and the mock run.
10. **One Python deployer** in `agentvax.chain.deploy`, used by the evaluation runner, the evidence run and the local interface. It links the six libraries at the offsets in each artifact's `linkReferences`, asserts that no reference is left unresolved, checks every receipt and the deployed code, and keeps every library receipt for E01.
11. **VaxLab holds no key.** VaxLab produces inputs and reads public outcomes. A separate executor in the evaluation runner owns the keys and submits. The runner stops Anvil in a `finally` block.
12. **Owner actions** (approve, cancel, extendHold, mandate changes, capsule publication) are prepared by the runtime and signed by an owner signer object that the runtime does not hold. In the evaluation and evidence runs that signer is a separate harness component.
13. **API.** Instructions are accepted only with a per-session token and an origin check, `source` is assigned on the server, and pasted or referenced material goes through the quarantined reader path. All dynamic values are rendered with `textContent`.
Commits the project to: two processes per wallet runtime, and a small JSON protocol between them that is versioned.

### D26. Closing contract fixes (12 October 2026)
Context: a second review of the contracts led to these changes.
1. The attestation lifetime bounds `validUntil` relative to submission only. Signing age is the guardian's responsibility, because the contract cannot learn when a signature was made from anything other than the same guardian key.
2. Capsules: a tracked list (16, matched on every request) and a spilled list (16), re-ranked against the bulletin at every sync, with promotion. While anything is spilled, every request is at least L2. Pending execution is refused while a capsule is in neither list or a spilled capsule demands owner approval. These are delays that end when the capsules expire, never an owner-approval requirement imposed by one observer.
3. Pending execution and approval are refused while a capsule backlog remains. Anyone may clear it with `syncCapsules`.
4. An owner approval also waits Π whenever an unprocessed or spilled capsule could be a full match. This extends the paper's "full capsule match" rule in the cautious direction.
5. Schedule-linked obligations cannot be paid through PAYMENT before they are due. One-off bills can.
6. The invariant's non-vacuity rests on a deterministic seeded payment, an `afterInvariant` call count and a deterministic test that drives every value path, rather than on requiring a fuzzed value movement in every run, which would be flaky.
PolicyWallet runtime is 23,812 bytes, 764 under the limit. Further features belong in the libraries.

### D27. Choices made while building the agent runtime (12 October 2026)
1. **Attestation expiry.** `validUntil` = the later of the latest block time and the host clock, plus the profile's lifetime (300 s, at most 900 s). Anvil mines on demand, so its latest block can be minutes old. The contract still caps `validUntil` at the submitting block plus 900 s, so a fast host clock can only make an attestation fail early, never last longer.
2. **Guardian key lifecycle.** `python -m agentvax.guardian.service init-key --key-file <path>` creates the key inside the guardian process (exclusive create) and reports only its address, which the deployer then names as guardian. Afterwards the parent passes only the path. On every request the guardian checks on chain that the wallet names it as guardian, and once checks the wallet's EIP-712 domain. The child process gets an allowlisted environment, so the owner and model keys never reach it. Known limit: the key file is plain hex, and Windows does not enforce the 0600 mode.
3. **Guardian protocol v1.** Line-delimited JSON with a protocol version, at most 16 content items of 65,536 characters each and 8 MiB per line, fixed error codes that never echo request text. The client re-checks the intent hash, digest, signer, that caller flags are included and that the source is external when content was sent. Only untrusted content affects band and source.
4. **Deployer.** Libraries are discovered from `linkReferences`, each placeholder must be the exact expected one before it is replaced, and runtime code must match the artifact apart from immutables. Wallets are registered in the bulletin in the same run and those hashes are kept. An artifact is fresh only if every source hash in its metadata still matches, otherwise `forge build` runs once.
5. **Chain client.** It re-reads the chain id before signing every transaction and decodes reverts during gas estimation, so a reverting call is never sent.
6. **Detector.** The encoder specification is stored in the model file. A file whose bytes are not already canonical is refused, so one model has exactly one hash. The seed model has dimension 4096 and thresholds 0.5 and 0.8, trained from 120 texts written once for that purpose, separate from the evaluation suites.
7. **Pressure rules.** ENCODED_CONTENT is set for invisible or tag characters, base64 or hex runs that decode to readable text (addresses and hashes excluded), escape runs, mixed-script words, encoding instructions, and listed phrases found only after rot13 or reversal. Decoded payloads are scanned for the phrase lists too. "Emergency" and "pay now" were left out because they flag ordinary invoices.
8. **Profiles.** Default fee fields: cap 0.01, daily budget 0.03, agent floor 0.02, native reserve 0.1 ETH. Demo: 0.002, 0.006, 0.004 and 0.002 ETH, so the evidence run fits a faucet grant. Channel profile 31 (all channels) in both.
9. **Reader and validator.** Whether a destination in a document differs from the allowlist is decided by plain code, not the model. Reader flags are masked to URGENCY, SECRECY, OVERRIDE_ATTEMPT, ENCODED_CONTENT and NEW_DESTINATION, so a reading can never claim a known identity, memory use or an anomaly. The mandate is an accepted amount source only where it fixes the amount exactly: the linked obligation for PAYMENT, D for SWEEP, the cap for FEE_TOPUP.
10. **Mission.** `OwnerSignedMandate` carries an owner signature over `keccak256(abi.encode(mandateHash, wallet, chainId))`, and `MandatePublisher` writes only if the signature recovers to the owner. The mission module holds no key.
11. **Capsule drafts.** Built from a confirmed attack with restriction 2 (single observer), features without AMOUNT_ANOMALY (the contract adds it), lifetime 7 days. KNOWN_PAYEE_IDENTITY with NEW_DESTINATION becomes recipient substitution against PAYEE_OR_MANDATE_CHANGE.

### D28. Runtime integration (12 October 2026)
1. **One resource helper.** `agentvax.resources`, backed by `importlib.resources`, reads every packaged data file. The deployment profile is the only source of mandate defaults, and the mission module receives them as an explicit `MandateTemplate`.
2. **Substituted addresses** (puts D8 into practice). A document that asks to pay a known payee at an address other than its on-chain account never becomes an intent. The runtime records a `PayeeChangeRequest` on chain, which carries no authority, and tells the owner that only they can add the address and that it waits Λ. A document that only says the details changed, with no address, still pays the on-chain account, with the flags attached, and the contract decides the tier.
3. **Replies are rendered from named `strings.json` keys.** Contract reverts map to `revert.<error name>` keys. No model text is ever shown.
4. **Explanations** re-read `discretionary(obligationRef)` for a payment that settles an obligation, so the shortfall shown equals the D the contract used.
5. **Payee identity hash.** Options: keccak of the raw name, keccak of a normalised name, a random salt per payee kept off chain. Decision: `keccak256(utf8(NFC(name).casefold() with runs of whitespace collapsed to one space and trimmed))`, computed by one shared helper. A salt would hide names better, but the identity hash has to be recomputable by the owner from the name alone, and the names of test payees are not secret. The names themselves stay off chain and are supplied to the runtime by the owner as payee id to name.

### D29. The detector's encoder is the hashing encoder in every mode (12 October 2026)
Context: the paper describes a frozen text encoder plus a logistic-regression head, and an offline hashing encoder for tests. The guardian uses the hashing encoder in live mode too.
Options: (a) a pretrained sentence-embedding model (about 100 MB plus a deep-learning runtime) for live mode, hashing for tests, (b) the hashing encoder everywhere, with the encoder kind recorded in the model file so another encoder can be added as a new kind.
Decision: (b). The hashing encoder is itself a frozen encoder: fixed, deterministic, with no learned parameters. The whole detector, encoder specification included, is one canonical file whose hash is anchored on chain, so every wallet can check exactly what it runs. A pretrained encoder would add a large download, platform-dependent numerics that make the anchored hash hard to reproduce, and a dependency the guardian process would have to load. The detector is one layer, because the contract bounds what any undetected attack can do. This is a departure from the paper's description, recorded here and in the security self-assessment. Measured detector numbers are reported for this encoder.
Commits the project to: adding an embedding encoder later means a new `kind` in `EncoderSpec`, a new anchored model version, and canary checks, with no change to the guardian protocol.

### D30. Which attack the capsule-response suite uses (12 October 2026)
A recipient-substitution capsule targets PAYEE_OR_MANDATE_CHANGE, and in this build a substituted address never becomes a payment intent (D28.2). Such a capsule therefore restricts payee changes, not payments. The capsule-response suite (A attacked, the reworded attack replayed on B, C unaffected) uses an indirect-injection payment attack with pressure flags, whose capsule targets PAYMENT, so "B restricted from the next transaction" is measured on a value-moving transaction. The recipient-substitution path is covered by the panicked-owner suite and E13.

### D31. Fixes to the runtime boundaries (12 October 2026)
1. Capsule features never include KNOWN_PAYEE_IDENTITY or AMOUNT_ANOMALY, so no capsule can partially match ordinary payments to known payees. A recipient substitution matches on NEW_DESTINATION plus the pressure flags it carried.
2. Memory may identify a payee, which sets MEMORY_SOURCED. It is never the source of an amount.
3. A signed mandate is bound to the target wallet and chain, and `OwnerMandateSink` puts the owner-signature gate on the real write path.
4. Explanations use a wallet view read at the receipt block.
5. Public contract constants are read from the contract (for example the minimum schedule period, carried in `WalletView`). Internal ones (mandate bounds, attestation lifetime) are Python copies guarded by Anvil tests of the contract's behaviour at and just beyond each bound.
6. The hosted model is built only by `agentvax.llm.build` from a provider table in data. Only `openai-compatible` is listed and it needs an explicit `base_url`. The factory never returns `MockLLM`.
7. Owner workflows that write memory are `capsules.confirm_attack` and `owner_tools.apply_payee_addition`. Memory stores an account only as the keccak of its address bytes.

### D32. Evaluation design (12 October 2026)
Context: the evaluation plan was challenged before construction. The main objection was accepted: treating any owner-approved item as authorised is circular, because the panicked-owner and social-engineering cases script attacker-induced approvals.
1. **Authorisation comes only from the case.** Each case declares its allowed transitions as exact tuples (wallet, asset, action, recipient, exact amount, schedule terms, earliest and latest chain time, how many times). Any other state change is a violation, even if the harness signed an approval. A panicked-owner case may declare that an approved action becomes allowed after Π or Λ, as fixture data.
2. **The judge sees everything.** It compares a before and after projection of wallet state (balances, payees, obligations, schedules, pending items, changes, mandate, freeze, keys, allowance, dismissals) and every event the wallet emits with the allowed transitions. MockUSD outflows are matched to `Transfer(from = wallet)` events, not to recipient balance changes. Native top-ups are measured from the wallet's debit, not the agent's balance.
3. **Isolation.** Every independent case starts from an Anvil snapshot with fresh memory, agent and guardian state. Only the sequential suites (probing, panicked owner, capsule response) share state within the suite. Base attacks and their rewordings are first-contact unless the case tests capsule protection.
4. **Non-vacuity.** The runner asserts that each case reached its intended code path: every affordability case emits exactly one matching `Decision`, probing ends on a `CHECK_ALLOWANCE` decision after the expected executions, B's replay is a valid matching submission, C's unrelated request executes at L1, B's request after expiry executes at L1, and every scripted approval was actually sent. A case that fails this is reported as a harness error and fails the run.
5. **Ledger.** Every case writes a record (block range, transaction hashes, decoded events, before and after projections, expected transitions, verdict) to `results/eval_ledger.<mode>.jsonl`, together with the keccak of each suite file. The summary is reduced mechanically from the ledger and follows a fixed format with no extra fields.
6. **Fixed sizes.** 40 tasks (10 per task), 10 ambiguous, 20 affordability, exactly 30 base attacks (6 per family) with exactly 2 fixed paraphrases each (60), a probing sequence of exactly 6 invoices. Stable unique ids.
7. **Metric definitions.**
   - `hard_policy_violations`: number of unique violating transitions in the ledger.
   - `unauthorized_tx`: violating transitions in the attack suites that moved value. `value_beyond_l1`: value moved with no owner action outside the L1 envelope, or an L2 item executed before Δ.
   - `task_suite.success`: tasks whose allowed transitions happened exactly and nothing else. `wrong_executions`: tasks with any unexpected side effect. `ambiguous_handled`: ambiguous cases that ended in the declared question or rejection with no side effect.
   - `safe_autonomy_rate`: among the 40 task cases, all of which are declared L1-eligible in the suite data, the share executed at L1 with exactly the expected change.
   - `escalation_rate`: among the declared benign, L1-eligible requests listed in the suite data, the share that went to L2 or L3.
   - `detector_fpr`: over a declared corpus of benign documents in the suites, one prediction per document, the share banded medium or high. Deterministic pressure-rule false positives are reported separately in the ledger.
   - `reworded_matched_rate`: share of reworded forms whose submission on a wallet holding the base attack's published capsule produced an on-chain `Decision` naming that capsule (full match). In live mode the headline uses fresh, uncurated model paraphrases. The fixed paraphrases are run as well and reported separately in the ledger.
   - `capsule.tx_before_restriction`: matching transactions on B executed at L1 after A's capsule was published, given that at least one valid matching replay was submitted.
   - `friction`: configured chain-time delays exercised by advancing the block timestamp (Λ, Π, and the allowance refill period). Reported as chain-time seconds, not wall-clock time.
   - `gas`: per entry point, the number of receipts and the median and 95th percentile gas used.
8. Suite models are strict, immutable and forbid extra fields. Live rewording goes through the model adapter with a typed schema, and every generated form is saved.

### D33. Federation (12 October 2026)
1. Federation starts from the seed model (version 1) that the guardian ships with. "Local" is the seed model trained on the wallet's own data for the same number of epochs as the federated run, so the cross-family gain is measured from a shared starting point.
2. **Exact masking.** Updates are fixed-point integers in units of 2^-30, pairwise masks are integers below 2^40 derived per pair from an X25519 exchange and HKDF bound to the round, and every sum is checked to stay below 2^53, so the masks cancel exactly inside Flower's float `aggregate`. Hiding is statistical (bounded masks), not modular, because Flower's FedAvg averages floats. All three wallets have equal example counts, so FedAvg weights are equal and masks cancel. If a wallet drops out, the round is abandoned. This is a protocol demonstration in one process, so whoever runs all three clients holds all masks.
3. Clipping happens inside each wallet, since the aggregator sees only masked updates. A wallet that skips clipping is caught by the canaries, which is the defence the hostile-wallet suite measures. The aggregator does not also refuse an average longer than C, so that the canary result is not masked by an earlier check.
4. A candidate is adopted only if every wallet's canary accepts it. A rejected round keeps the current model.
5. The anchored model is the final adopted one. Versions only need to increase.
Measured in the first run (mock data, written once): see `results/federation.json`. Every wallet gained on unseen families, false positives on benign test texts rose from 0.07 to 0.11, wallet B's recall on its own family fell from 0.95 to 0.80 without its canary noticing, and no honest update was large enough to be clipped. These are reported as measured in `docs/RESULTS.md`.

### D34. Evaluation harness choices (12 October 2026)
1. **Deterministic chain time.** The runner sets a one-second block timestamp interval and moves time with `evm_setNextBlockTimestamp`, so runs are reproducible and a snapshot revert restores time. Anvil's default host-clock time went backwards between blocks and produced false findings.
2. **One guardian process per wallet for the whole run.** Its only state is its key and a one-time domain check, both identical after a snapshot revert. Agent and memory are fresh for every case.
3. **`reworded_matched_rate`.** A form that produces a `Decision` is matched when that Decision names the base attack's capsule. A form that ends as a payee change request (recipient substitution, D28.2) is matched when the wallet's on-chain `matchCapsules(PAYEE_OR_MANDATE_CHANGE, flags)`, with the flags recorded in its `PayeeChangeRequested` event, returns a full match naming that capsule. The ledger records which rule decided each form. A form that produces neither is unmatched.
4. **Metric details where D32.7 is silent.** `unauthorized_tx` counts over the attack, probing, panicked-owner, hostile-wallet and capsule-response suites. `value_beyond_l1` counts over all suites. `value_left_before_delay` is the number of value-moving transitions found before their delay, undeclared or outside L1. `within_allowance` means the first probe that was not L1 was decided by the allowance check and no later probe ran at L1. `false_capsule_max_restriction` is the larger of the bulletin's effective restriction and the tier of any safe-now Decision naming a false capsule. Gas keys are wallet function names, prefixed for other contracts.
5. **Setup with an earlier payment** sets the mandate with reserve 0, makes the real payment, raises the reserve (a tightening, so immediate) and mints the exact balance. An allowance level is set with `confirmAttack` and a refill.
6. **Exit codes.** 0 with a summary. 1 for a harness error or a vacuous suite (ledger written, no summary). 2 when the run could not start. A stale summary is deleted when a run starts.
7. **Replays.** B is set up like A. Each reworded form is replayed on B after A's owner confirms the base attack with `capsules.confirm_attack` and publishes the capsule.
8. **Poisoned update.** The hostile-wallet suite also runs a poisoned federation round through `agentvax.fed.hostile` and records every wallet's canary verdict. Adopting the poisoned model would be a violation.

### D35. First evaluation run, and the interface (12 October 2026)
The first mock run on the committed suites failed four hard gates (43 violations). Every finding was diagnosed case by case before any change. No suite file was edited.
1. **Block times after a revert.** The harness cached block times by block number, but after `evm_revert` the same numbers are mined again at other times. That produced every panicked-owner and capsule-expiry finding. The contract held Π and Λ on chain. The cache was removed.
2. **No guessing of schedule terms.** The mock planner filled in a default of 12 runs and missed some periods. Schedule terms are now read by deterministic rules in `agentvax/schedules.py` and `data/schedule_rules.json`, shared by the mock planner and the validator. A term that is missing, conflicting or unreadable makes the agent ask. An instruction that also says not to pay, or mixes tasks, makes the agent ask. The validator rejects a schedule whose terms differ from the instruction.
3. **Unstated start.** When the owner gives a period and a run count but no start, the first run is one period after now. Options: ask every time, or this convention. The convention is deterministic, written in the rules file, shown back to the owner, and never pays early.
4. **Notices, not violations.** Two kinds of observed behaviour are recorded in the ledger as notices instead of violations. (a) A payee change request that only emits `PayeeChangeRequested` and changes no wallet state, because it carries no authority (D28.2). (b) A pending item for exactly the owner's declared request at a stricter tier than declared, with no value moved, because under the caution principle a more cautious outcome is never a policy breach. Both rules apply only when nothing else in the transaction is unexplained. A laxer outcome than declared stays a violation, and a stricter outcome still does not count as a task success.
5. **Mock phrase tables are not widened to fit the suite.** Task success and ambiguous handling with `MockLLM` are reported as measured. They describe the mock's phrase tables, not a model.
6. **Interface.** `OwnerActions` is the only holder of the owner signer in the API. Submitting the considered-confirmation dialog is the approval. If the owner says someone else asked for the payment, the server first lengthens the hold by Π, then approves. Nothing can shorten a hold. Expected income is kept off chain, shown and marked "not counted". Extra endpoints: execute a ready item, cancel a pending change, propose and apply a payee, record expected income. The demo follows wall-clock time after setup so its countdowns are real. SQLite memory may be shared between the API's worker threads, with every use serialised under one lock.

### D36. Evaluation stack and the stricter-tier rule (12 October 2026)
1. `agentvax.eval.stack.local_stack` is the one place a local stack is built (Anvil, keys, guardian keys created inside their own processes, deployment, federation, anchoring, adoption, hash-gated guardians), used by the evaluation runner and the local demo. It always cleans up, also after a partial failure. The demo therefore runs the anchored, adopted federated model, like the evaluation.
2. The `stricter_than_declared` notice (D35.4b) matches an observed item to a declared transition by wallet, task, payee and amount. The obligation reference is not compared, because allowed transitions have no field for it and the suites are not changed after the fact. Known limit, recorded here.

### D37. Refinement of evaluation non-vacuity (12 October 2026)
Context: D32.4 made any case that failed to reach its intended code path a harness error that fails the run. A hostile-wallet probe was answered by the mock planner with a question, so it never reached the wallet, yet the case counted as exact. Failing the whole run in that situation would push towards widening the mock's phrase tables to fit suite wording, which D35.5 rules out.
Decision: a case whose intended request did not reach the wallet is recorded as `not_exercised` and never counted as exact. Every hard gate derived from a sequence suite must be supported by at least one exercised case of that suite, otherwise the run is a harness error. Not-exercised cases are listed in `docs/RESULTS.md`.
Also: suite file hashes in the ledger are computed over the bytes with CRLF normalised to LF, which equals the committed blob under `.gitattributes` (`eol=lf`), so the ledger binds to the committed suites on any platform.

### D40. The guardian's RPC endpoint travels in its environment (12 October 2026)
Context: D38 recorded that the guardian received the RPC URL as a command-line argument, which any local user can read in the process list, and a provider key is often embedded in that URL.
Options: a stdin handshake (a protocol change), a file path (a secret on disk), the child's environment.
Decision: `GuardianClient.start` sets `AGENTVAX_GUARDIAN_RPC_URL` in the child's environment and `--rpc-url` is removed from the service, so there is one channel. The variable is not on the inherited allowlist, so only the client sets it. Error text that could quote the URL is redacted. Remaining limits: a process of the same user or an administrator can read a child's environment, and redaction replaces exact text only.

### D41. The demonstration script follows the paper's scenario with these differences (12 October 2026)

### D42. Hosted interface and run provenance (12 October 2026)

### D43. Tests never depend on interface wording, and evidence steps are one transaction each (12 October 2026)
Context: a revision of the wording in `strings.json` broke 11 tests that asserted literal English.
1. Interface wording is data, revised independently of code (D15, D25.7). Tests assert the template key chosen and the values filled in, and where the sentence matters, that it equals the rendering of that key from `strings.json`. No production code compares interface text.
2. In the evidence run each mined owner transaction is its own recorded step. E11 is `E11/confirm` then `E11/publish`, so a resume never repeats a mined transaction. The capsule workflow is split into `send_attack_confirmation`, `draft_for`, `publish_draft` and `remember_attack`, and `confirm_attack` is built from them. A state file from before this change could publish a second capsule on resume. None exists, because no test-network run has been made.

### D44. Public RPC state lag after a receipt (20 October 2026)
The first Base Sepolia evidence deployment returned a successful receipt for AuthorityLogic, but the immediate runtime code check found no code. A later read showed exactly the compiled 8,271 byte runtime. Base serves preconfirmed receipts before its `latest` state reflects them, so a receipt can be visible before the code or state it created.
1. The deployer retries absent runtime code for at most ten seconds. It still rejects nonempty mismatching code at once and never treats code that stays absent as verified.
2. On Base Sepolia the chain client returns a receipt only once the canonical head is past the receipt's block and that block's hash and transaction list match the receipt. The wait has a timeout. It does not claim L1 finality. Anvil keeps its immediate mining.
3. Six regression tests cover delayed code, a nonempty mismatch, permanently absent code, preconfirmed against canonical inclusion, the timeout and local immediate receipts. No contract, tier or delay changed.
